# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Fexer is a portrait-orientation iOS camera app: SwiftUI UI, AVFoundation capture, Core Image
filters, Metal preview. Deployment target iOS 26.0, Swift 6 with `SWIFT_STRICT_CONCURRENCY:
complete`, and **both `SWIFT_TREAT_WARNINGS_AS_ERRORS` and `GCC_TREAT_WARNINGS_AS_ERRORS` are
YES** — any compiler warning fails the build, not just errors.

The Xcode project (`Fexer.xcodeproj`) is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen)
from `project.yml`. **Never hand-edit the `.pbxproj`.** Any time you add, remove, or rename a
file under `Fexer/` or `Tests/`, run `xcodegen generate` before building — the project file is
a build artifact, not a source of truth, and a stale one will silently exclude your new file
from compilation (this has happened before in this repo).

## Commands

```sh
# Regenerate the Xcode project after adding/removing/renaming files
xcodegen generate

# Find a simulator destination id
xcrun simctl list devices available

# Debug build (simulator; no code signing needed)
xcodebuild -project Fexer.xcodeproj -scheme Fexer \
  -destination 'platform=iOS Simulator,id=<SIMULATOR_UDID>' \
  -derivedDataPath build build CODE_SIGNING_ALLOWED=NO

# Release build (validates whole-module optimization before archiving)
xcodebuild -project Fexer.xcodeproj -scheme Fexer -configuration Release \
  -destination 'platform=iOS Simulator,id=<SIMULATOR_UDID>' \
  -derivedDataPath build build CODE_SIGNING_ALLOWED=NO

# Full test suite (unit + UI)
xcodebuild -project Fexer.xcodeproj -scheme Fexer \
  -destination 'platform=iOS Simulator,id=<SIMULATOR_UDID>' \
  -derivedDataPath build test CODE_SIGNING_ALLOWED=NO

# Just unit tests (Swift Testing, Tests/Unit) or just UI tests (XCUITest, Tests/UI)
... test -only-testing:FexerTests ...
... test -only-testing:FexerUITests ...

# A single unit test (Swift Testing) or UI test (XCTest)
... test -only-testing:FexerTests/EditRecipeTests/validatedClampsOutOfRangeAdjustments ...
... test -only-testing:FexerUITests/FexerUITests/testSettingsOpensAndCloses ...

# Install + launch the built app on a booted simulator (quick manual smoke check)
xcrun simctl install <SIMULATOR_UDID> build/Build/Products/Debug-iphonesimulator/Fexer.app
xcrun simctl launch <SIMULATOR_UDID> com.nandanvarma.fexer
```

There is no separate lint step configured (no `.swiftlint.yml` in this tree) — the compiler's
warnings-as-errors setting is the enforced style gate.

## Architecture

Layers, in dependency order (each only depends on the ones above it):

- **`Domain/`** — pure value types with no I/O: `EditRecipe` (versioned, validated edit
  instructions — see `EditRecipe.validated`, which is the single place every field gets
  clamped), `LibraryItem`/`GeoTag`, `PhotoStyle` (the built-in LUT catalog), `CameraTypes`
  (phases, controls, capabilities, events). All `Codable`, `Hashable`, `Sendable`.
- **`Imaging/`** — stateless Core Image graph. `ImagePipeline.apply` builds the filter chain
  from an `EditRecipe`; `ImageRenderer` (actor) turns that into actual preview/export pixels
  and caches parsed `.cube` LUTs; `CubeLUT.parse` is a strict, bounded parser (rejects
  oversized files, bad domains, malformed rows); `ColorMath` turns per-band hue/sat/lum and
  curve adjustments into a synthesized adjustment cube.
- **`Camera/`** — the capture engine. `CameraOperating` is the protocol; `CameraService`
  (actor) is the real AVFoundation implementation, `SimulatedCamera` (actor, compiled only
  under `#if targetEnvironment(simulator)`) loops a bundled sample photo through the same
  interface so the simulator has a working (if fake) viewfinder. `FrameProcessor` is a
  one-frame "mailbox" (`Mutex`-guarded snapshot, not a queue) that decouples the capture
  thread from the SwiftUI/Metal render loop in `CameraPreview`. `PhotoDelegate`/`MovieDelegate`
  adapt AVFoundation's callback-based capture APIs to `async`/`await`.
- **`Library/`** — persistence. `CaptureStore` (actor) owns one directory per capture on disk
  and is durability-first: the original file is written and fsync'd *before* `record.json` is
  published, so a crash mid-write leaves an unpublished directory, never a corrupt record.
  `LibraryModel` (`@MainActor @Observable`) is the app-facing façade over the store, the
  renderer, and `PhotosExporter` (writes to `PHPhotoLibrary`).
- **`Features/{Camera,Editor,Library,Settings}/`** — SwiftUI screens paired with
  `@Observable` view models (`CameraModel`, `EditorModel`). Views stay declarative; state and
  side effects (capture sequencing, debounced preview re-render, undo/redo) live in the
  models.
- **`Infrastructure/`** — `Diagnostics` (OSLog + the `AppIssue` user-facing error type),
  `Preferences` (a single `Codable` settings struct in `UserDefaults`, with one-time migration
  from the previous app's separate keys), `LocationService`/`LevelService` (CoreLocation/
  CoreMotion wrapped as `@MainActor @Observable`, with `nonisolated` delegate callbacks that
  hop back via `Task { @MainActor in ... }`).
- **`App/FexerApp.swift`** — the composition root. It's the only file that chooses between
  `CameraService` and `SimulatedCamera` (`#if targetEnvironment(simulator)`) and wires up
  `PreferenceStore` → `CaptureStore` → `ImageRenderer` → `LibraryModel` → `CameraModel`.

### Patterns worth preserving

- **`CameraModel` takes `frames: FrameProcessor` as its own constructor argument** instead of
  reading `service.frames` through the `CameraOperating` existential. This is deliberate: the
  protocol declares `frames` without `nonisolated`, so reading it through `any CameraOperating`
  would force an actor hop per frame. Don't "simplify" this by removing the parameter.
- **Recoverable capture**: `CameraModel` holds a completed-but-unsaved photo in
  `pendingCapture` and exposes `retrySave()`; a failed disk/Photos write never silently drops
  the picture the user just took. Read `captureOne`/`persistPending`/`retrySave` in
  `CameraModel.swift` before touching capture completion or error handling.
- **`@Observable` properties bound through `@Bindable` dot-chains must be `var`**, even if
  never reassigned after `init`. SwiftUI's `@Bindable` dynamic-member lookup needs a
  `ReferenceWritableKeyPath`; a `let`-declared reference property (e.g. `CameraModel.
  preferences`) compiles fine on its own but breaks any view doing `$model.preferences.value.x`.
- **Resource lookups have no subdirectory**: `Bundle.main.url(forResource:withExtension:)` for
  `.cube` LUTs assumes XcodeGen flattens loose resource files to the bundle root. `project.yml`
  must keep `Fexer` as one `sources` entry — splitting it into `sources` (with an exclude) plus
  a separate `resources` block has previously caused the entire `Resources/` folder (LUTs,
  asset catalog, sample image, `PrivacyInfo.xcprivacy`) to be silently dropped from the build.
- Unit tests use **Swift Testing** (`import Testing`, `@Test`, `#expect`) in `Tests/Unit`; UI
  tests use **XCTest/XCUITest** in `Tests/UI`. Keep new tests in whichever style matches their
  target rather than mixing.
- Full end-to-end camera behavior (real lens switching, manual exposure/focus/white balance,
  RAW/ProRAW, Live Photo, 4K/60fps video, real permission prompts) cannot be verified on the
  simulator — `SimulatedCamera` only proves the UI and data flow. That needs a physical iPhone.

## History

`.archived/` holds the previous full implementation (SwiftUI + AVFoundation app, plus the
`web/` marketing site), preserved wholesale when the app was rewritten from scratch. It
predates the architecture and conventions above — don't port code from it without deliberately
re-reviewing it against the current patterns. The marketing site has not yet been rebuilt.
